01

You shouldn't need AWS to test S3.

Your application writes to S3, so now your test suite needs a bucket. The usual choices are a real cloud bucket, a mock that only implements the three calls this one test happens to make, or a container heavier than the thing you're testing.

Stow is the fourth option. A real S3 API, on your own machine, that costs nothing and leaves no trace. If your code can talk to S3, it can talk to Stow — same SDK, same SigV4, same PutObject.

02

One call. Private S3.

A session is the shortest path from nothing to a working S3 client. It starts a private server on an ephemeral port, creates a bucket, waits until the server reports itself ready, and hands back a client already pointed at it. On close it stops the server and deletes the data directory.

test/s3.test.ts TypeScript 
import { PutObjectCommand, GetObjectCommand } from "@aws-sdk/client-s3";
import { withStow } from "@chs/stow-s3";

await withStow(async ({ s3, bucket }) => {
  await s3.send(new PutObjectCommand({
    Bucket: bucket,
    Key: "input.json",
    Body: '{"task":"summarize"}',
  }));

  const got = await s3.send(new GetObjectCommand({ Bucket: bucket, Key: "input.json" }));
  await got.Body.transformToString();
});
// the server and its data are gone by the time this resolves

Four guarantees matter when something else is running the test suite, and the server enforces all of them:

A session cannot

  • Inherit your cloud config
  • Outlive your process
  • Report a limit it hasn't checked
  • Grow past 16 MiB / 1,000 objects

It does

  • Strip STOW_*, S3_*, AWS_* first
  • Exit if its parent dies, killed or not
  • Read capabilities off the server
  • Enforce limits server-side, every request

S3 where you need it.

The protocol is the same everywhere. What changes is how you reach it: four language surfaces, three storage modes, and the S3 clients you already have.

Storage is selectable per server: memory for throwaway work, filesystem when data has to survive a restart, and run-through when you want a local S3 in front of an upstream bucket you already have.

Implemented

  • Buckets: create, list, inspect, delete
  • Objects: put, get, head, copy, delete
  • List with prefixes and pagination
  • Range reads
  • Conditional reads and writes
  • MD5, CRC32, CRC32C, SHA-1, SHA-256
  • Multipart uploads
  • Presigned requests
  • SigV4 authentication

Not implemented

  • Versioning
  • ACLs and bucket policies
  • Lifecycle rules
  • Replication
  • Event notifications
  • Object tagging and lock
  • S3 Select
  • KMS-backed encryption

Give your tests a bucket. Not your AWS account.

It is free, it is Apache 2.0, and it is one binary. If it breaks, the issue tracker is the fastest way to tell me.
