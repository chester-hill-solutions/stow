# Changelog

## Unreleased

- **Breaking, data loss in the response.** A multi-object delete reported the inverse of what it did, on one of the three backends. `DeleteObjects` returns the keys it deleted, and the S3 handler copies that slice straight into the `<Deleted>` elements of the response — but the workspace backend returned the keys that *survived*. A client deleting three objects was told it had deleted the one that was never there, and told nothing about the two that were actually gone. The deletions themselves were correct; the report was the complement. `DeleteObjects` had no doc comment on the `Store` interface, so the meaning of its return value was unspecified and three implementations chose: two returned the keys deleted, the third returned the other list, and nothing said which was right. The same omission lost the partial-progress case — a failure partway through returned `nil` instead of the keys already removed, so a caller retrying the remainder could not skip what had succeeded, turning a recoverable partial failure into a second round of deletes against keys that were gone. The interface now documents both halves, the workspace backend returns deletions and keeps its progress, and a contract case asserts that every key it reports as deleted is genuinely absent. The workspace backend's own test had recorded the complement as expected behaviour — it deleted a key, confirmed two lines later that the key was gone, and asserted that the *other* key was the one returned — so the defect was pinned rather than merely uncaught. A second case runs the S3 surface against all three stores, because the handler inherits whatever the store returns and a store-level test alone does not prove the wire.

- A multipart completion with exactly one part returned the wrong ETag on two of the three backends, and no backend rejected a completion with no parts at all. S3 treats a one-part completion as a single-part object and returns that part's own ETag verbatim; the `-{partCount}` suffix belongs to genuinely multipart objects, where the digest covers the concatenated part digests. The memory and filesystem backends returned `md5(md5(body))-1` where S3 returns `md5(body)` — a double hash, with a suffix. The workspace backend had it right, in a `len(parts) > 1` conditional the other two did not share, so the rule was written three times and correct once. It is now one function, `storage.CompletionETag`, called by all three, and the correctness of the previously-correct backend is pinned by a contract case so it cannot silently regress back. The returned value changes for single-part completions, so a client that stored the old ETag will get `412` on a conditional write until it re-reads; that client was already holding a value S3 would not have issued. Separately, the emptiness check existed in two backends and was missing from the third, so the same empty completion produced a `500` on two stores and a zero-byte object published under the caller's key on the third. That check now lives in `ValidateMultipartPartNumbers` and returns `ErrInvalidPart` rather than `ErrInvalidUpload`, which the S3 surface does not map and which therefore fell through to a 500 — misreporting a malformed request as a server fault and inviting a retry that could never succeed. Both rules were absent from the contract suite, so all three backends passed it.

- **Breaking, install.** Every documented install path was unresolvable. `site/agent.md` and `site/llms.txt` — the two files an agent is most likely to be handed first — opened with `npm install @chs/stow-s3`, `pip install stow-s3` and a `go get`, and all three failed: nothing was published to npm or PyPI, and the Go module path was `.../stow-s3` while the repository was still `.../stow`, so no published version of it could resolve. An agent following the instructions stopped at the first one, and the failure presented as a registry or network problem rather than a documentation one. The repository is now `chester-hill-solutions/stow-s3`, matching the module path, the npm scope, the PyPI name and the binary — every user-facing document already said so, including the repository URL. The Go module is published and installs. npm and PyPI are not published yet, and the documentation now says so instead of implying otherwise; the TypeScript and Python clients are usable from a source checkout, and all three paths were run end to end before being documented. The `v0.1.0` tag predates the rename and cannot be fetched under the new module path; `@latest` and `v0.2.0` are unaffected. `scripts/check-install-surface.mjs` makes publication status a single declared fact and fails when the documentation and that declaration disagree, which is the check this was missing; the release workflow additionally resolves each published target against its registry. See issue #3.

- **Breaking, macOS.** The parent-death watch was never armed on macOS, and the server logged itself as protected while it was not. `Watch` had two independent defects at once. It registered an `EVFILT_PROC`/`NOTE_EXIT` filter and then closed the kqueue descriptor as it returned, with nothing ever reading the event; kqueue filters are scoped to the open descriptor, so closing it discarded the registration. And it read `kevent()`'s return value as a count of registered changes when the kernel reports how many events it placed in the eventlist, which is always `0` for a registration-only call, so every pid including the real parent was rejected with `ErrNotParent`. Either defect alone is fatal, and fixing only the descriptor would have left the watch broken while looking correct. The descriptor is now held for the process lifetime with a goroutine blocked on it, raising `SIGTERM` when the parent exits — the same disposition `PR_SET_PDEATHSIG` produces on Linux, so both platforms terminate identically whatever the server's own signal handling is. The arm/death race is closed by re-checking the parent after registration, as Linux does. A kqueue error after a successful arm is now fatal rather than silent, because continuing would leave a server that believes it is watched and is not. macOS is a first-class release target, so this leaked a process and a data directory on every killed session. A `macos-latest` CI job was added, because every job ran on ubuntu and the kill test therefore never executed on the platform whose implementation it exists to protect; `release.yml` only cross-compiles darwin, which proves the binary builds and nothing about its lifecycle. The new job failed on its first run and is what found the `kevent()` defect. See issue #4.

- The filesystem backend rejected object keys between 128 and 1024 bytes, even though `ValidateKey` accepts up to 1024. The key was hex-encoded into a single path component and hex doubles the length, so anything over 127 bytes failed with `ENAMETOOLONG` and surfaced to the caller as a `500` for input it was entitled to send. It also broke interchangeability between the two drivers: the embedded driver is memory-only, so the same call succeeded on one and failed on the other. Long keys are now split across shard directories holding chunks of the same reversible encoding. Shard directories carry a prefix that cannot occur in hex, which matters more than it looks: without it a record file and a shard directory share one name space, so a key whose encoded length fell exactly on a chunk boundary wrote its record *file* to a path that a longer key sharing the same hex prefix had to descend through, and the longer write failed with `ENOTDIR`. Because hex preserves order, any two keys with a common byte prefix collide, so this was the common case rather than an exotic one. A path component's form now decides whether it is descended into, with no `stat` required. Keys that fit stay flat, so existing data directories are unaffected: long keys never wrote successfully, so no stored object depends on the layout. Deletes prune the shard directories they empty, which would otherwise accumulate for the life of the data directory, and the list walk descends only into shards it recognises. No test covered a long key anywhere, which is why this reached a release. See issue #5.

- `check-generated`, and the CI step that diffs the committed WebAssembly artifact, could never pass. Four of the seven required checks on `main` were permanently red, and had been since before `0.2`. Two independent causes, neither of them a source change. The Go version was never pinned: `go.mod` said `go 1.24` and all ten `setup-go` steps used `go-version-file: go.mod`, which resolves to the newest `1.24.x` rather than a fixed patch, so a locally built artifact never matched a CI rebuild. Adding a `toolchain` directive on its own would not have fixed it either, because Go uses a newer installed toolchain instead of downgrading to the one named. `.go-version` now pins the exact patch for every step in `ci`, `release`, and `live`, and the `toolchain` directive in `go.mod` makes a local build fetch that same patch. Separately, `copy-wasm-assets.mjs` used `copyFile`, which carries the source mode across, and the two places `wasm_exec.js` comes from disagree about it: the tarball toolchain ships it `0755`, the module-cache toolchain `0444`. Git records only the executable bit, so on a fresh checkout the copy gained the bit and the diff failed on a mode change with identical contents — which is why the gate passed in a working tree and failed on the runner. The copy now sets the mode explicitly, and both committed assets are `0644` rather than the previous mix of `0644` and `0755`. See issue #6.

- The TypeScript client now honors `timeoutMs` and `signal` on `openStow` and `withStow`. Both were declared on `EphemeralStowOptions` and never forwarded to the spawner, so a caller's timeout was silently replaced by a hardcoded ten seconds and an abort signal did nothing. An already-aborted signal now fails before a process is spawned, and an abort during startup stops the child rather than leaving it running.
- The client honors the region the server reports. The readiness protocol carried a `region` field, the client parsed it, and then discarded it in favour of a hardcoded `us-east-1`, which signs against the wrong region for any non-default server. The server gained `--region` so the field can actually vary, which is what made the behavior testable; the default is unchanged.
- The readiness descriptor is no longer parsed mid-record. A chunk boundary can fall anywhere, and the trailing unterminated fragment was being handed to the JSON parser; a syntax error there was thrown from a stream callback, so the rejection never reached the promise and startup hung until the timeout, already cleared. Only a newline-terminated record is parsed now, a parse failure rejects, an oversized record without a newline is reported as a protocol violation rather than silently truncated, and the descriptor's `end` and `error` events are handled. The `end` case defers by one turn so a child exit is still reported as a child exit rather than as a pipe failure.
- `StowProtocolError` gains a `cancelled` code. Cancellation was reported as `internal`, which tells a caller nothing about whether retrying could ever help.
- **Breaking, security.** Admin and metrics routes now require a credential. `--allow-public-admin` was a bare boolean and the only gate, so enabling it exposed the `outbox/retry` and `outbox/discard` actions to any client that could reach the port, with no authentication. The flag is now deprecated and ignored. Remote admin routes require `STOW_ADMIN_TOKEN` or `--admin-token`, sent as `X-Stow-Admin`; the two outbox routes require it on loopback as well, since loopback is not a privilege boundary. Read-only routes (`health`, `status`, `inspect`, `metrics`) still work on loopback without a token, so `stow doctor` needs nothing. Rejections are `404` rather than `403` so the route's existence is not advertised, and the token comparison is constant time.
- **Breaking, security.** CORS no longer reflects the request's `Origin`. It previously echoed whatever arrived, or sent `*` when the header was absent, so any website a developer visited could read responses from their local stow — including bucket contents — using the credentials the SDK had already placed in the page. Loopback origins are permitted by default, which is the case a local dev server has; anything else must be named with a repeatable `--cors-origin`, and `*` restores the old behavior only when asked for explicitly. Every response now carries `Vary: Origin`, without which a cache can serve one origin's allow header to another, and a preflight from a disallowed origin is refused with `403`. This wires `Config.CORSOrigins`, which was declared and never read.
- **Breaking, safety.** `STOW_POLICY=mirrorWrites` no longer enables live upstream writes on its own. Previously the policy set `AllowLiveWrites` whenever `STOW_ALLOW_LIVE_WRITES` was *unset*, so the absence of a variable was the enabling condition, and a staging `.env` containing the policy plus shared credentials was enough to propagate mutations to a real bucket under the default auto-detected mode. `STOW_ALLOW_LIVE_WRITES=true` or `--allow-live-writes` is now required and is sufficient under either policy; an explicit `false` is a refusal the policy cannot override. Reads still use run-through, and writes still succeed locally. See `docs/adr/0005-live-write-requires-explicit-consent.md`.
- Report the effective write policy from one place. The banner, the server status payload, and startup validation each derived it independently, which is how the banner could claim `mirrorWrites` while the adapter refused the write. A configured-but-inert policy now reports `mirrorWrites-disabled` instead of reading as active.
- A run-through server on the memory backend with `mirrorWrites` configured and no live-write consent now starts instead of being refused. It performs no propagation, so requiring the filesystem backend for it was rejecting a configuration that works.
- **Breaking, safety.** `Stow.start({ cleanSlate: true })` was an unguarded recursive delete of whatever path the caller passed, including the home directory, and was reachable from the published `dist/`. A reset now requires a `.stow-owner` marker that the server writes when it initializes a data directory, and refuses the filesystem root, the home directory, the working directory, and any ancestor of them. `resetOwnedData` is the new name; `cleanSlate` is a deprecated alias with identical checks. A pre-existing data directory without the marker is refused rather than deleted, so upgrading requires one manual removal. See `docs/adr/0006-owned-data-directory-reset.md`.
- Local mode is now proven to make zero upstream requests rather than assumed to. Store construction is one function that never builds an upstream client in local mode, and a test sets the full hazardous environment, exercises the object operations against a recording upstream, and requires zero hits.
- Close the 0.2 remediation gate with race-safe server lifecycle, atomic filesystem object records, backend parity checks, write-ahead durable outbox recovery, ordered per-key propagation, admin metrics/retry controls, and expanded conformance coverage.
- Add a memory-only direct embedded Go runtime with explicit paginated results, bounded/TTL separate run-through caches, and a versioned `js/wasm` host bridge without changing the process/endpoint TypeScript contracts.
- Coordinate file-backed outbox workers across processes with expiring per-entry claims and a filesystem lock.
- Reconcile an attempted outbox entry against upstream before re-propagating it: a retried put whose upstream ETag already matches the immutable local version, or a retried delete whose object is already absent, is acknowledged instead of replayed. The remaining duplicate-delivery window is an upstream that cannot be read during recovery, or an object another writer has since replaced.
- Reject durable outbox files written by a newer schema revision instead of silently dropping claim and reconciliation fields; unversioned files migrate, and attempted legacy entries are marked for reconciliation.
